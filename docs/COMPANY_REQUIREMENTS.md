# Соответствие задаче Zunami / «Инносети»

Источник: оригинальный одностраничный PDF компании, `source-materials/ZUNAMI_COMPANY_BRIEF.pdf`. Текст сохранён рядом; подробное ранее полученное ТЗ находится в `source-materials/1-INNOSIGHT_full_answer.txt` и `SPECIFICATION.txt`. Документы используются как требования к продукту, а не как разрешение выполнять внешние действия. Контакты, Telegram-приглашение, часы эксперта и сроки в PDF сохранены как контекст; сообщения от имени пользователя не отправлялись.

## Суть задачи компании

Визуализировать, какие поля и типы GraphQL-схемы затрагиваются автоматизированными тестами, какие остаются без внимания. Сервис располагается между тестами и GraphQL-сервером, перехватывает запросы, собирает статистику и представляет покрытие.

| Требование                        | Реализация                                                                                        | Проверка                                                                                       |
| --------------------------------- | ------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Между тестами и API               | Настоящий POST/GET GraphQL Proxy, без изменения бизнес-ответа                                     | HTTP integration сравнивает direct/proxy responses, заголовок request ID, ошибки и статусы     |
| Подключить существующие автотесты | Раздел «Прогоны автотестов»: endpoint + X-Innosight-Capture, API для CI                           | E2E создаёт прогон, HTTP-запрос с токеном проходит через nginx и upstream                      |
| Поля конкретного запуска          | Отдельные capture_sessions и request_events.capture_id, уникальные AST coordinates                | Integration: два запроса прогона дают ровно 5/99 полей, обычный запрос исключён                |
| Типы конкретного запуска          | Доля object/interface-типов с выбранными output-полями; список выбранных/невыбранных типов        | Тот же HTTP-тест проверяет 3 выбранных типа; JSON содержит числители/знаменатели               |
| Видимые пробелы                   | Таблица всех полей с поиском и фильтром «Не затронуты», карточки типов, глобальный Graph Universe | E2E фильтрует выбранные поля и проверяет реальные строки; граф проверяется отдельным сценарием |
| Сохранение и история              | PostgreSQL, миграция 002 поверх неизменённой 001, история и JSON-отчёт                            | Integration перезапускает backend, находит прежний прогон, проверяет export                    |
| Обновление во время тестов        | SSE после фактического сохранения, React Query invalidation                                       | E2E видит 0% → 3% без перезагрузки страницы                                                    |
| Корректная методология            | Selection coverage отделено от проверяемых assertions Test Lab                                    | Integration/E2E подтверждают, что capture не увеличивает Verified coverage                     |
| Схема меняется                    | Прогон закреплён за schema_id, старый токен отклоняется при смене схемы                           | Integration получает CAPTURE_SCHEMA_CHANGED и проверяет сохранённый старый отчёт               |

## Что добавлено сверх минимальной задачи компании

Dashboard с реальными графиками, Graph Universe, безопасная история запросов, Playground, встроенный Test Lab с assertions, Demo Lab с шестью сценариями, semantic change impact, snapshots, JSON/CSV/печатный отчёт, оценка эффекта по пользовательским предположениям, разрешённые внешние HTTPS-проекты. Они дополняют основную цепочку, а не заменяют её визуальными заглушками.

## Как честно объяснять результат

- Отправка поля в selection не доказывает, что resolver выполнился или данные верны. При resolver error факт selection сохраняется и отдельно показана ошибка.
- Внешний раннер не передаёт INNOSIGHT результат assertions автоматически. Его прогон показывает выбор полей автотестами. Verified появляется только из проверок встроенного Test Lab.
- Input types, scalar и enum не являются output-полями и не входят в denominator field/type coverage прогонов. Interface selections раскрываются через schema/AST; методология одинакова с основной аналитикой.
- Отчёт не содержит переменных, тел ответов и токена прогона. Результаты внешних тестов и исходные payload хранятся у владельца раннера.
- Это проверяемая локальная демонстрационная поставка. SSO/RBAC, multi-instance deployment, WebSocket subscriptions, file upload и incremental delivery не заявляются реализованными.

Фактические команды и свежие результаты см. `RELEASE_1_1.md`. Исторические файлы `RELEASE_AUDIT.md`, `QA_RESULTS.json` и часть старых JSON описывают выпуск 1.0.
