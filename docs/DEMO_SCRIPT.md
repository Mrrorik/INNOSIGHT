# Пятиминутная демонстрация

## Подготовка

1. `docker compose up -d --build --wait`.
2. Открыть http://localhost:3000, закрыть onboarding или перейти из него в Demo Lab.
3. **Demo Lab → Reset Demo → Сбросить Demo**. Дождаться уведомления. Другие проекты не затрагиваются.
4. Открыть Overview: baseline — три реально выполненных запроса, 25/99 полей, **25.25% selection**, **0% verified**. UI округляет проценты до одного знака: 25,3%.
5. Лучше использовать окно шириной 1440 px. На ноутбуке 1280 px и мобильном интерфейс также проверяется.

После Reset бизнес-fixtures восстанавливаются, пользовательские demo tests удаляются, восемь встроенных тестов остаются. История, snapshots и кандидат SDL demo project сбрасываются. Время ответа зависит от машины; не обещайте заранее конкретный P95.

## 0:00–0:40 — проблема

Открыть Overview.

> «У GraphQL API десятки полей, но мы редко знаем, какие действительно выбирают клиенты и что проверено тестами. INNOSIGHT показывает оба факта раздельно. Здесь 25 наблюдавшихся полей, но пока ни одного тестового подтверждения».

Открыть Graph Universe. Выбрать заголовок `Product`, затем любое поле в панели. Показать наблюдения и объяснение статуса. Поля можно нажимать непосредственно в узлах; заголовок выбирает тип.

## 0:40–1:30 — настоящий запрос и измеримый рост

Открыть Playground → пример **«Открыть слепые зоны»** → Execute query.

Показать реальный JSON, название операции, новые поля и положительное изменение coverage. Значение зависит от уже собранной истории; после Reset этот пример содержит новые поля.

Открыть Live Requests через «Исследовать запрос». Открыть строку и показать schema coordinates, HTTP status, origin `live` и безопасную структуру без литеральных значений.

Для сильного эффекта держать Overview во второй вкладке: coverage обновится через SSE без refresh.

## 1:30–2:15 — управляемый инцидент

Demo Lab → **D · Trigger an Incident** → Запустить.

> «Это три настоящих вызова: ошибка платёжного resolver при HTTP 200, медленный resolver и validation error. INNOSIGHT различает транспортный статус и GraphQL errors».

Открыть Live Requests → «Только ошибки». Показать `PaymentIncident`, безопасный error code и path. Перейти в Risk Intelligence: объяснить корреляцию ошибок с выбранными полями, не утверждать, что каждый красный resolver неисправен.

## 2:15–3:10 — подтверждение тестами

Test Lab → **Запустить весь набор**. После чистого Reset и без собственных mutations ожидаются **8 passed / 0 failed**.

Раскрыть один результат: показать настоящие assertions `data… equals/exists/minLength`. Verified coverage растёт с 0 до фактического значения прогона. Показать зелёные поля на схеме.

> «Обычный трафик не повышает verified coverage. Тест без assertions либо с failed assertion не подтверждает поле. Даже успешный тест ожидаемой ошибки не добавляет data coverage».

Если до демонстрации вы меняли commerce data через mutation, выполните Reset: fixtures снова станут предсказуемыми.

## 3:10–4:10 — центральная коммерческая ценность

Demo Lab → **B · Generate Real Traffic** (если ещё не запускали: это добавит `LegacyClient`). Затем **F · Detect Breaking Changes**. Открыть Change Impact.

Показать две реально сохранённые схемы:

- `User.email`: String! → Int!.
- `Product.legacyPrice`: поле удалено.

Показать observed operations `Customers`, `LegacyClient` и связанные tests.

> «Перед изменением схемы мы видим потенциально затронутые запросы клиентов и тесты. Это помогает выбрать, что проверить до выпуска. Если поле не наблюдалось, это ещё не доказывает отсутствие потребителей».

Активная схема не меняется: кандидат сравнивается отдельно, живой API продолжает работать.

## 4:10–5:00 — результат, который можно передать команде

Reports → создать snapshot «После проверок» → **Открыть отчёт**. Показать coverage, риски, проблемные операции, change impact и методологию. Кнопка печати позволяет сохранить PDF. CSV и JSON реально скачиваются.

Business Impact → изменить предположения ROI и явно назвать их предположениями.

> «INNOSIGHT объединяет факты использования, тестовое подтверждение и оценку изменений. Главная ценность — увидеть слепые зоны и потенциальных потребителей до выпуска API».

## Альтернатива: автоматический проход

Demo Lab → **Start Demo · все 6 сценариев**. Каждый эксперимент выполняет backend-действия; журнал и before/after основаны на реальных данных. После завершения можно открыть Requests, Tests и Change Impact. Результаты экспериментов сохраняются в PostgreSQL и восстанавливаются при повторном открытии Demo Lab.

## Восстановление

- Нет upstream: Settings показывает соединение; `docker compose logs demo-api server` и `docker compose ps`.
- Неожиданные результаты тестов после mutations: Reset Demo.
- UI устарел после остановки сервера: EventSource восстанавливается и перечитывает данные; при необходимости refresh браузера.
- Порт занят: остановить другой локальный процесс или согласованно изменить Compose port mapping. В контейнерах сервисы используют внутренние имена.
- `docker compose restart server demo-api web` сохраняет аналитику; бизнес-fixtures Demo API восстановятся.
- Не удалять volume для обычного восстановления.

Ни один KPI не фиксирован ради презентации. Названия товаров, пользователи и заказы — явно демонстрационные business fixtures. Трафик, ошибки, latency, coverage, test results и schema diff — фактически вычисленные результаты.

## Дополнительно: автотесты компании (версия 1.1)

Откройте «Прогоны автотестов», создайте «CI build 42». Замените endpoint тестов на указанный Proxy, добавьте X-Innosight-Capture и выполните query из встроенного curl-примера. Страница покажет покрытие только этого запуска, затронутые типы и поля. Переключите фильтр на «Не затронуты», объясните оставшиеся пробелы. Завершите прогон и скачайте JSON. Токен закрывается; обычные запросы без него не входили в отчёт. Укажите, что selection автотестов не выдаётся за доказанные assertions. Полная инструкция: START_HERE_RU.md, раздел 6.
