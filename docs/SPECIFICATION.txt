Концепция проекта для хакатона «Инносети — GraphQL Coverage Proxy»

Я предлагаю сделать не просто анализатор покрытия GraphQL API, а **полноценную платформу наблюдаемости, тестирования и анализа рисков GraphQL**, которую можно продемонстрировать вживую и потенциально предложить компаниям как коммерческий продукт.

Главная идея: **создать систему, которая показывает, какие части GraphQL API реально используются, какие никогда не проверялись, где возникают ошибки и что необходимо протестировать в первую очередь.**

# 1. Продуктовая идея

INNOSIGHT — платформа GraphQL Observability, Coverage Analytics & API Quality Intelligence.

Она устанавливается между GraphQL-клиентом и существующим GraphQL API и анализирует реальные проходящие запросы.

Основной поток:

GraphQL Client → INNOSIGHT Proxy → Target GraphQL Server

Параллельно:

Proxy → Analysis Engine → PostgreSQL → Analytics API → Live Dashboard

Система должна позволять командам разработки и QA отвечать на вопросы:

- Какая часть GraphQL-схемы реально запрашивается клиентами?
- Какие поля ни разу не наблюдались в запросах?
- Какие поля покрыты успешными автоматизированными проверками?
- Какие операции вызываются наиболее часто?
- Какие запросы медленные?
- Где возникают GraphQL-ошибки и HTTP-ошибки?
- Какие изменения схемы потенциально сломают существующие клиенты?
- Какие части API требуют тестирования в первую очередь?
- Как изменилось покрытие после запуска новой серии тестов?
- Какие поля имеют наибольшую наблюдаемую эксплуатационную значимость?

Продукт должен одновременно приносить пользу разработчику, QA-инженеру, тимлиду и техническому руководителю.

ВАЖНО: строго различай три понятия:

1. Schema selection coverage — доля полей схемы, которые встречались в наблюдаемых GraphQL-операциях.
2. Verified test coverage — доля полей, которые были задействованы в успешно выполненных зарегистрированных тестовых сценариях с проверяемыми assertions.
3. Runtime health — реальные ошибки, время ответа и статистика запросов.

Нельзя выдавать присутствие поля в AST за доказательство фактического выполнения resolver. Нельзя выдавать наличие запроса за пройденный тест.

Все показатели должны иметь документированные формулы и ограничения.

# 4. Реальный GraphQL Coverage Proxy

Это сердце продукта. Реализуй его в первую очередь.

## Основные требования

Proxy должен:

- Принимать GraphQL HTTP-запросы.
- Передавать их на заранее настроенный upstream GraphQL-сервер.
- Возвращать клиенту фактический ответ upstream.
- Сохранять корректные HTTP-статусы.
- Обрабатывать GraphQL errors внутри HTTP 200.
- Измерять время ответа.
- Учитывать сетевые ошибки.
- Поддерживать query, mutation, variables и operationName.
- Корректно обрабатывать aliases.
- Корректно раскрывать fragments и inline fragments.
- Обрабатывать несколько операций в документе с учётом operationName.
- Учитывать директивы @skip и @include при известных значениях переменных.
- Правильно работать с вложенными selections, interfaces и unions.
- Исключать introspection-поля из пользовательских показателей покрытия.
- Поддерживать стандартные JSON POST-запросы.
- Корректно обрабатывать GraphQL over HTTP GET там, где он применим.
- Не допускать двойной отправки запросов.
- Не изменять бизнес-семантику upstream API.

Используй graphql-js для анализа AST. Не пытайся реализовать GraphQL-парсер регулярными выражениями.

Наблюдаемые поля идентифицируй через координаты схемы, например:

`Query.products`

`Product.price`

`User.email`

Учитывай тип, которому принадлежит поле, а не только название поля.

## Корректность анализа

Для обычных операций вычисляй статически выбранные поля с учётом доступной информации о типах, фрагментах и директивах.

Для неоднозначных runtime-ветвей интерфейсов и union-типов не утверждай, что resolver обязательно был выполнен.

Отдельно регистрируй:

- Observed selections.
- Successful operations.
- Failed operations.
- Test-verified fields.

Если конкретная транспортная возможность, например multipart upload, SSE streaming, WebSocket subscriptions или persisted query без доступного текста операции, не реализована полностью, явно обозначь её статус. Не выдавай неподдерживаемый сценарий за работающий.

Базовый JSON GraphQL over HTTP должен работать полноценно.

## Безопасность

- Не сохраняй Authorization headers и API-ключи в журнале.
- По умолчанию не сохраняй чувствительные значения variables и тело response.
- Храни безопасную информацию об операции, её структуре и метаданных.
- Ограничивай размер запросов.
- Добавь timeout для upstream.
- Применяй ограничения на настройку upstream.
- Исключи возможность использования proxy как произвольного открытого HTTP-прокси.
- Защити административные действия и изменение настроек в режиме реального подключения.
- Не допускай SSRF через свободное указание произвольных URL.
- Обеспечь корректное завершение соединений при отмене клиентского запроса.

Для демонстрационного режима допустим отдельный удобный доступ без внешней авторизации, но это должно быть явно обозначено.

# 5. GraphQL Schema Intelligence

Создай модуль анализа GraphQL-схемы.

Возможности:

- Загрузка схемы через introspection.
- Импорт SDL.
- Поддержка актуальной схемы проекта.
- Сохранение версий схемы.
- Визуализация типов и полей.
- Подсчёт coverage.
- Обнаружение никогда не наблюдавшихся полей.
- Анализ наиболее часто используемых полей.
- Обнаружение deprecated-полей.
- Сравнение версий схемы.
- Выявление breaking и dangerous changes.

Для сравнения схем используй семантические механизмы graphql-js, а не текстовый diff.

Отдельно покажи:

- Total object/interface fields.
- Observed fields.
- Unobserved fields.
- Selection coverage percentage.
- Verified test coverage percentage.
- Deprecated fields usage.
- Top operations.
- Schema changes.

Не смешивай input fields с output fields в одном знаменателе coverage без объяснения.

При невозможности получить introspection предоставляй возможность загрузить SDL.

Добавь поиск по типам и полям.

# 6. Главная визуальная особенность — Graph Universe

Реализуй выдающуюся интерактивную визуализацию GraphQL-схемы.

Это один из ключевых элементов демонстрации.

Используй React Flow или эквивалентный движок.

Каждый GraphQL-тип — узел графа.

Связи между объектами — рёбра.

Поля, наблюдавшиеся в запросах, визуально отличаются от ненаблюдавшихся.

Пример цветовой семантики:

- Зелёный — есть успешное тестовое подтверждение.
- Синий — поле наблюдалось в запросах.
- Жёлтый — требует внимания.
- Красный — зафиксированы ошибки или повышенный вычисленный риск.
- Серый — поле не наблюдалось.

Если поле имеет несколько свойств, показывай основной статус и дополнительные индикаторы, не создавая неоднозначности.

Возможности графа:

- Масштабирование.
- Панорамирование.
- Поиск.
- Фильтрация по статусу.
- Выбор типа.
- Просмотр полей.
- Просмотр частоты использования.
- Просмотр связанных ошибок.
- Подсветка выбранной операции.
- Подсветка цепочки связанных типов.
- Мини-карта.
- Автоматическая компоновка.
- Режим fullscreen.
- Кнопка Reset View.

При получении нового GraphQL-запроса соответствующие узлы должны обновляться без перезагрузки страницы.

Сделай плавную анимацию обнаружения активности.

При выделении поля пользователь должен видеть объяснение, почему у него именно такой статус.

Не делай декоративный граф, не привязанный к реальным данным.

# 9. Risk Intelligence Engine

Создай объяснимую систему выявления потенциально проблемных частей GraphQL API.

Не используй фиктивный AI.

Лучше реализуй качественный детерминированный движок рекомендаций, чем имитацию искусственного интеллекта.

Возможные факторы риска:

- Поле часто выбирают, но оно не покрыто проверенными тестами.
- Повышенная доля GraphQL errors.
- Высокая latency у операций.
- Использование deprecated-полей.
- Breaking changes между версиями схемы.
- Отсутствие наблюдений для критически важных полей.
- Резкий рост ошибок после определённого периода.

Risk score должен быть вычислимым и объяснимым.

Для каждого finding показывай:

- Severity.
- Затронутое поле или операцию.
- Причину.
- Наблюдаемые данные.
- Рекомендованное действие.
- Возможное влияние.
- Ссылку на связанные события.

Добавь представление «Что исправить в первую очередь».

Не называй эвристический risk score доказанной уязвимостью безопасности.

## Как получить максимально качественный результат от Codex

После того как Codex реализует основную версию, я рекомендую отправить ему ещё одно короткое сообщение — для финальной доводки:

Проведи финальный Product Release Audit проекта INNOSIGHT.

Считай, что завтра продукт будут оценивать потенциальные покупатели, а главная цель — убедительная демонстрация работающей технологии.

Проверь весь проект от Docker Compose до пользовательского интерфейса. Выполни доступные unit, integration и E2E-тесты. Пройди через основные пользовательские сценарии.

Особое внимание удели реальной работе GraphQL Proxy, математической корректности coverage, изменению показателей после запросов, успешности тестовых сценариев, обновлению Live Dashboard, работе Graph Universe и демонстрации ошибок.

Найди и устрани дефекты, неработающие действия, плохие UX-решения, визуальные недочёты и проблемы совместимости.

Улучши дизайн до уровня качественного коммерческого SaaS. Особое внимание удели главному экрану и Demo Lab.

Создай безотказный сценарий пятиминутной демонстрации с возможностью сброса состояния и повторного запуска.

Не заменяй реальные функции моками. Не подделывай метрики. Не удаляй работающий функционал ради косметических улучшений.

После исправлений повтори доступные проверки. Представь точный список проверенных возможностей, непроверенных возможностей и оставшихся ограничений.

Не заканчивай на отчёте о проблемах — исправь всё, что можешь исправить в текущей среде.

## Что тебе понадобится для запуска

Codex с доступом к рабочей папке
Он должен иметь возможность создавать файлы проекта и запускать команды, а не только выдавать текст.

Docker Desktop или Docker Engine
Для запуска frontend, backend, базы данных и тестового GraphQL API.

Браузер
Для проверки интерфейса, графиков, демонстрационных сценариев и API Playground.

Целевая команда запуска:

`docker compose up --build`

После успешной сборки целевой адрес приложения — `http://localhost:3000`.

Это именно предполагаемый результат работы Codex, а не уже созданный и проверенный проект. Для такой большой задачи потребуется реальная реализация и несколько итераций проверки. Структура с `AGENTS.md`, этапами работы и проверками также соответствует рекомендациям по работе с Codex.

## Самая важная особенность для продажи проекта

Я бы сделал центральным коммерческим аргументом не само наличие 10 графиков, а конкретную функцию **Change Impact Intelligence**.

Представь: компания собирается удалить или изменить поле GraphQL. INNOSIGHT сразу показывает, встречалось ли это поле в реальных запросах, сколько операций его используют и какие тесты с ним связаны.

Это превращает обычный анализ покрытия в инструмент оценки последствий изменения API. При наличии достаточной истории наблюдений он может помочь команде избежать поломок клиентских приложений. Такой сценарий гораздо понятнее потенциальному покупателю, чем просто красивый процент coverage.

**Формула сильной защиты:** показать проблему → вызвать её на настоящем API → обнаружить её в INNOSIGHT → выполнить проверку или проанализировать изменение → показать измеримый результат.

Если Codex действительно реализует всю эту цепочку и она пройдёт практическую проверку, у тебя будет не просто эффектный хакатонный прототип, а серьёзная основа продукта, который можно развивать и предлагать командам разработки.
