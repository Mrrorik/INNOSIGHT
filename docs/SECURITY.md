# Безопасность и границы поставки

INNOSIGHT 1.1 запускается локально. Все опубликованные Compose-порты привязаны к loopback. Демо-действия и чтение аналитики доступны без login; это осознанный режим локальной демонстрации, а не изоляция нескольких арендаторов на публичном сервере.

## Реализовано

- Административные действия с внешними проектами требуют ADMIN_TOKEN. Сравнение токена constant-time при совпадающей длине.
- Внешние upstream — только точные HTTPS URLs из серверного UPSTREAM_ALLOWLIST. URL credentials/query/fragment запрещены, redirects отключены. Нет формы произвольного HTTP forwarding.
- Серверные upstream credentials задаются в UPSTREAM_HEADERS_JSON и не возвращаются API настроек. В Playground разрешённые заголовки живут в памяти вкладки, не в истории событий.
- Запросы/ответы ограничены по размеру, upstream timeout 10 секунд, ограничение частоты API. Неподдерживаемые протоколы явно отклоняются.
- История request_events хранит координаты полей и обезличенную структуру AST. Значения arguments/variables, тела response, cookies и credentials туда не записываются. Ошибки сохраняются в нормализованном виде без произвольного текста upstream.
- Токен прогона: 32 криптографически случайных байта, выдаётся один раз, в БД только SHA-256, не передаётся upstream и не хранится в localStorage. Завершение блокирует дальнейшие запросы с этим токеном. На внешних проектах создание/завершение требует admin.
- Прогон закреплён за схемой, старые evidence не смешиваются с новой схемой. Управление проектом защищено от гонки с in-flight proxy requests в одном backend-процессе.
- SQL-запросы параметризованы. Миграции проверяют checksum, старые файлы изменять нельзя. Печатные отчёты экранируют пользовательский текст.
- nginx задаёт security headers; серверные контейнеры работают от node/nginx, не от root. Offline-руководство не содержит секретов и внешних скриптов.

## Что учитывать владельцу

- Capture token отделяет статистику запуска, но не является полной аутентификацией GraphQL API. Upstream auth по-прежнему нужен, когда его требует API.
- Успешный response assertions Test Lab подтверждает только указанные пути, не весь ответ. Тестовые query и fixtures хранятся как конфигурация тестов: не помещайте в них production secrets/PII. Гарантия redaction относится к журналу request_events, а не к намеренно зарегистрированным тестовым данным.
- PostgreSQL volume и backup содержат конфигурацию, SDL и аналитику. Названия типов/полей сами могут быть конфиденциальны. Не публикуйте базу или .env.
- Нет автоматической retention/архивации; история и отчёты могут расти. На больших потоках нужны SQL aggregation/лимиты, нагрузочное тестирование и отдельный дизайн хранения. Поставка проверяется на demo/integration-нагрузке, не заявляет production throughput/SLA.
- Для публичной эксплуатации необходимы gateway auth, reader permissions/RBAC, TLS, CSRF/identity policy по выбранной модели, управление секретами, backup/restore drills, мониторинг, аудит зависимостей, retention и rate limits по идентичности.
- Текущие coordination locks локальны одному процессу. Несколько backend replicas требуют распределённого управления состоянием и pub/sub вместо process-local SSE bus.
- Не открывайте Docker daemon или PostgreSQL в интернет и не отключайте TLS validation для корпоративного API.
